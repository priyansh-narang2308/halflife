| D13 | Use Tavily's `max_age_hours` (content freshness, new in Oct 2026) as the core freshness lever, `X-Project-ID` = tenant and `X-Session-Id` = report for attribution inside Tavily | Directly matches Tavily #01 and gives tenant attribution that doesn't depend on Bifrost alone. | D14 | Redis for the semantic cache = Docker `redis:8.2.2` on **127.0.0.1:6380**, ephemeral (no RDB/AOF) | Homebrew Redis 8.6.3 has no search module (`FT.*` → unknown command) and Bifrost's Redis vector store requires it (`framework/vectorstore/redis.go:82`). The official `redis:8` image bundles search, vectorset, JSON, bloom and timeseries. Port 6379 belongs to your `falkordb` container. The embedded `chromem` store stays as a zero-infrastructure fallback. |
| D15 | Module path `github.com/maximhq/bifrost/plugins/halflife` | Same namespace as the fork's other plugins, so `make setup-workspace` and the `replace` in `transports/go.mod` work like the built-ins. Authorship is ours and is recorded in `UPSTREAM_DIFF.md`; the path is only the fork's module namespace. |
| D16 | Halflife is placement `pre_builtin`, order `math.MinInt`, fixed in code (not configurable) | Post-hooks run in reverse (`core/bifrost.go` `RunPostLLMHooks`; `handlers/middlewares.go`), so Halflife's post-hooks run last and see the final response, and its pre-hook runs before the semantic cache can short-circuit. Cost: its own hook time falls outside the telemetry plugin's measurement, so overhead is measured directly instead (Task 15). |
| D17 | Capture hands off through a per-request `*slot` pointer opened in `HTTPTransportPreHook`, not through context values | Observed: the gateway gives transport hooks and core hooks different root contexts. Values flow transport → core (copied) but not back, so anything `PostLLMHook` sets is invisible to `HTTPTransportPostHook`. A pointer copied forward is shared by both. |
| D18 | Fallback status comes from `BifrostContextKeyFallbackIndex`, not `RoutingInfo.IsFallback` | Core sets `IsFallback` on the response only after post-hooks run (`core/bifrost.go` ~6413), so it is always false inside `PostLLMHook`. The fallback index is set before each attempt. |
| D19 | Report IDs are `hlr_` + UUIDv7; the header is set only on captured (buffered) responses | Time-ordered IDs list reports in creation order without an extra index, and `google/uuid` is already a gateway dependency (`go.sum` unchanged). Streaming responses get their headers before their post-hooks run, so they can't carry a report ID; they aren't captured in M1 anyway (Task 14). |
| D20 | Tenant = governance virtual key, recorded as ID and name only | `x-bf-vk` is a credential. Governance resolves it to an ID/name in its `PreLLMHook`, which Halflife's `PostLLMHook` can read. A unit test asserts the secret never appears in a capture. |
| D21 | Audit queue: drop when full, never block; withdraw the report header for dropped captures | Halflife must never add latency to a request because the verifier is slow. A report header for a report that will never exist would be a broken promise to the client. |
| D22 | Shutdown drains for `drain_timeout_seconds` (default 5), then cancels; queued leftovers counted as abandoned | Graceful by default but bounded, so a gateway restart can't hang on Tavily. An audit that ignores cancellation gets 1 more second, then `Cleanup` returns an error rather than blocking. |
| D23 | Recursion guard keys on the verifier's governance virtual key ID | The verifier's LLM calls go through the gateway like any tenant's, so they reach Halflife's hooks. The VK ID is already resolved by governance, is not a secret, and gives the verifier its own budget. A request header would let any client opt out of auditing. Tavily relay calls never reach the hooks (Halflife is not a `RelayPlugin`). |
| D24 | `X-Halflife-Status` on every response, not just audited ones | Clients and judges can see that a stream was deliberately not audited in M1, instead of inferring it from a missing report header. |
| D25 | Overhead is measured against an A/A control on fresh gateways, and the headline number is one request in flight | Two processes on one laptop differ by chance; without a control, noise reads as overhead (or as a speed-up). The first version reused one baseline gateway for both comparisons, and Halflife came out 400–700 µs "faster" at 16 in flight because the baseline had served twice the traffic. At 16 in flight the control itself moves ±200 µs at p50, so only the sequential run resolves Halflife's cost. |
| D26 | Mock embeddings: a 64-dim hashed bag of content words (stop words removed), unit length | Semantic caching needs an embedding provider. A real one costs credits and is not deterministic across runs. Hashed words make paraphrase similarity predictable ("How much does the Acme Cloud Pro plan cost?" vs "What does Acme Cloud Pro cost?" = 0.926) and testable offline. It proves the cache's mechanics, not embedding quality. |
| D27 | The cache baseline runs Bifrost's cache alone, without Halflife | Task 16 establishes what the built-in cache does before Halflife changes anything, so later freshness behaviour can be compared to it. Halflife and the cache together start in Task 17. |
| D28 | A cache hit gets the report of the answer that filled the entry, not a new audit; links are an in-memory LRU (100k) until the report store (Task 25) | The cached answer is byte-for-byte the audited one, so re-auditing it would spend Tavily credits on known work. A hit is audited afresh only when no report is known (restart, dropped report) or the report is another tenant's (possible only with identity scoping off): one tenant is never pointed at another's report. |
| D29 | Plugin tests drive Bifrost's real core and real `semantic_cache` plugin, on the in-process chromem store, wrapped so a test can hold cache writes | Hook order, short-circuits and the cache's async write are what Halflife depends on; a hand-written fake would test our assumptions about them, not them. Wrapping the store's `Add` makes the write timing controllable for Task 19's race. |
| D30 | Halflife caps the cache TTL (min of its own and the client's) rather than replacing it; "Redis TTL" is checked as the entry's `expires_at` field | A client asking for a shorter life should get it; a longer one would let an unaudited answer outlive Halflife's freshness window. Bifrost's cache sets no Redis key expiry (`TTL` = -1) and filters on `expires_at` at lookup, so that field is the TTL to confirm. |
| D31 | A stale answer found inside the cache's write window (default 35 s = the cache's 30 s write timeout + 5) sends its whole cache partition past the cache until a delete after the window succeeds | A delete can't remove a write that hasn't landed, and Halflife can't see when it lands. Bypassing only the same question would still let paraphrases semantically hit the late write. The partition (`x-bf-cache-key`, or the default key) is the narrowest scope that covers every request that could be served that entry, under any identity-scoping mode. The cost is uncached traffic in that partition for up to the window, only after a stale finding. The bypass uses a cache type the cache doesn't know, so it skips lookup, write and embedding, and the cache logs one warning per bypassed request. |
| D32 | The relay allows only the routes Halflife uses (`POST /search`, `POST /extract`, `GET /usage` as non-billable) and prices each call as `usage.credits` × $0.008, Tavily's pay-as-you-go rate | An allowlist keeps the verifier key from reaching costly endpoints (crawl, research) through the relay. Pricing the credits Tavily reports keeps Bifrost's charges aligned with Tavily's bill. A call without `include_usage` is billed by Tavily but charged $0 by Bifrost (measured), so Halflife's client always sends it, and reconciliation against `/usage` stays in the plan. |
| D33 | `X-Halflife-Status` is set only on POSTs outside `/relay/`, `/mcp` and `/api/` | Those routes run the transport hooks but never produce an answer, so they were labelled `failed`, `verifier` or `streaming`, which was misleading. A rejected chat request (no key, provider error) still gets `not-audited; reason=failed`. |
| D34 | The verifier keeps its own short-lived record of searches and never sends the same query twice within an audit window | Live: an identical query came back from Tavily's cache in 0.29 s and still cost a credit. Halflife pays per search, so the duplicate is pure waste. To build with the verifier (Tasks 24, 31). |
| D35 | Spend is reconciled against Tavily's `/usage` from a delayed read, never from a read taken right after the calls | `/usage` still showed 0 used immediately after 7 credits were spent, and a minute later. Bifrost's relay log is the per-call record; `/usage` is the account total, read late (Task 38). |
| D36 | Budgets are soft under concurrency; Halflife bounds the overshoot with its own concurrency and treats a 402 as "budget spent, not verified", never retried within the window | Measured: governance checks spend before a call and charges after it, with nothing reserved for calls in flight, so 10 concurrent searches all passed a $0.02 budget ($0.088 charged). The overshoot per budget is at most `workers` (default 2) × the costliest call (advanced search, $0.016) per gateway: $0.032 at the defaults. Retrying a 402 would only add refused calls. |
| D37 | Risk A: each tenant gets its own verifier virtual key, inside the tenant's customer, with a budget below the customer budget; a shared verifier key is only for single-tenant setups | Measured (Task 23): per-tenant keys charge the tenant (key + customer budget), keep one tenant's heavy verification from refusing another's, and put the customer on every relay-log row. A shared key charged none of the tenants, let Acme exhaust it so Globex and Initech were refused, and left `X-Project-ID` at Tavily as the only per-tenant record. Inside the customer, verification and app spend share one cap: when Initech's verification spent its customer budget, Initech's app was refused too, so the verifier key's budget must be the smaller. Consequence for Task 24: config maps tenant key ID → verifier key, the recursion guard covers every verifier key, and a tenant with no verifier key is not verified (reported as such). |
| D38 | The M1 verifier picks one claim with a keyword heuristic and records evidence without judging it; no answer is marked stale until the judge exists | The task is to prove the path (capture → relay → Tavily → report) with real attribution and spend. A heuristic is deterministic and free; a judgement from keyword overlap would produce verdicts that look authoritative and aren't. Reports say `not_judged`, and cache eviction stays off until a model-based judge with typed comparators (Tasks 27-34) can justify it. |
| D39 | Reports live in a bounded in-memory store and are served only behind the gateway's dashboard auth | They hold the tenant's question and answer, so the endpoint is an operator view, like the rest of `/api`; a tenant-facing view that checks the caller's key is later work. In memory keeps M1 free of a schema; restarts lose reports, which the persistent store (Task 35) fixes. `gateway_url` is configured, not detected, because the plugin loader can't see the listen address; it defaults to Bifrost's `127.0.0.1:8080`. |
